Criar `apps/api/src/automacoes/cliente-leituras-financeiro.ts`.

Cabeçalho explicando, em três frases: (1) é o irmão de leitura de `invocar-agente.ts` — mesmo Bearer, mesmo `AbortSignal.timeout`, mesma classificação, mesmo `sanitizarErro`; (2) o que ele NÃO tem, e por quê: sem `aquecer()`/cache (não há pré-passo — a chamada nasce dentro do handler HTTP), sem `Idempotency-Key` (GETs e ações idempotentes por natureza do outro lado), sem transação (nada aqui grava em `plataforma.registros`); (3) `PLATAFORMA_LEITURA_TOKEN` é distinta de `PLATAFORMA_LANCAMENTO_TOKEN` por D4-02 — escopo mínimo.

Exportar:

- `interface OpcoesDoClienteDeLeituras { readonly destinoUrl: string; readonly token: string; readonly fetchImpl?: typeof fetch; readonly timeoutMs?: number; }` — `fetchImpl` e `timeoutMs` existem para o teste, exatamente como em `invocar-agente.ts` (padrão `fetch` e `10_000`).

- `type RespostaDeLeitura<T> = { readonly ok: true; readonly status: number; readonly corpo: T } | { readonly ok: false; readonly status?: number; readonly permanente: boolean; readonly code: string; readonly summary: string }` — o erro NUNCA carrega o corpo da resposta do `automation/`, só `code` + `summary` já saneados.

- `function classificarLeitura(status: number | undefined, corpo: unknown, erroDeRede: unknown): { permanente: boolean; code: string }` — copiar a semântica de `classificar` de `invocar-agente.ts`: `STATUS_PERMANENTES = [400, 401, 403, 404, 422]`; `retryable === true` no envelope → transitório; `retryable === false` → permanente (é assim que `503 CONFIGURACAO_AUSENTE` vira permanente); `429` e `5xx` sem `retryable` → transitório; sem `status` (rede/`AbortError`) → transitório com code `ERRO_DE_REDE`; status desconhecido → permanente, por segurança.

- `interface ClienteDeLeituras { ler<T>(caminho: string, opcoes?: { readonly query?: Record<string, string> }): Promise<RespostaDeLeitura<T>>; enviar<T>(caminho: string, corpo: unknown): Promise<RespostaDeLeitura<T>>; enviarArquivo<T>(caminho: string, arquivo: { readonly conteudo: Buffer; readonly contentType: string; readonly nome: string; readonly origem: string }): Promise<RespostaDeLeitura<T>>; }`

- `function criarClienteDeLeituras(opcoes: OpcoesDoClienteDeLeituras): ClienteDeLeituras`

Comportamento comum aos três métodos:
- URL = `${destinoUrl}${caminho}`, com `new URLSearchParams(query)` acrescentada quando houver query não vazia; nunca concatenar query à mão.
- Cabeçalhos: `authorization: Bearer ${token}`, `x-request-id: randomUUID()` (correlação, nunca idempotência), e `content-type: application/json` só em `enviar`.
- `enviarArquivo` manda o corpo BRUTO (o `Buffer`), com `content-type` do arquivo e os cabeçalhos `x-file-name` (nome) e `x-source` (o literal `crm-n1-financeiro`) — os mesmos nomes que `bank-statement-webhooks.ts` lê hoje (`x-file-name`, `x-source`).
- `signal: AbortSignal.timeout(timeoutMs)`.
- Erro de rede/timeout: capturar, NÃO relançar; devolver `{ ok: false, permanente: false, code: "ERRO_DE_REDE", summary }` com `summary` vindo de `sanitizarErro(erro, code).summary`.
- Resposta não-ok: ler o corpo com `await resposta.json().catch(() => undefined)`, passar a `classificarLeitura`, e devolver `{ ok: false, status, permanente, code, summary }` onde `summary` vem de `sanitizarErro(new Error(\`HTTP ${status} de ${caminho}\`), code).summary` — o caminho entra, a ORIGEM completa e o corpo NÃO.
- Resposta ok: devolver `{ ok: true, status, corpo }` com o JSON já parseado; se o parse falhar, tratar como erro permanente `RESPOSTA_INVALIDA`.
- Token vazio: `criarClienteDeLeituras` NÃO lança no boot; cada chamada com `token === ""` devolve `{ ok: false, permanente: true, code: "CREDENCIAL_AUSENTE" }` sem tocar a rede. Um token vazio nunca autentica, e o processo não deixa de subir por falta dele (a convenção de `optionalEnv` do outro lado).

Nada neste arquivo lê `process.env` — quem lê é `rotas/financeiro.ts` (04-05), que injeta `destinoUrl`/`token`. Isso é o que torna o teste possível sem env.

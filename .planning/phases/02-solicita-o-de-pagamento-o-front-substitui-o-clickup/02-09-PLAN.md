  <action>
Criar `apps/api/src/persistencia/credenciais-de-servico.ts` com:

`emitirCredencial({ workspaceId, nome, scopes, memberId })` — gera `id` legível curto (prefixo público, por exemplo `svc_` + 12 caracteres base32) e um segredo de 32 bytes de `crypto.randomBytes`, persiste `secret_hash = sha256(segredo)` e devolve `{ id, segredo }`. O segredo existe apenas no retorno desta chamada; nunca é gravado nem logado. O token apresentado no header é `\`${id}.${segredo}\``.

`resolverCredencial(token)` — separa `id` e `segredo` pelo primeiro `.`, busca a linha por `id`, compara `sha256(segredo)` com `secret_hash` usando `crypto.timingSafeEqual` (comparação em tempo constante), recusa se `state === 'revogada'`, atualiza `last_used_at` e devolve `{ id, workspaceId, memberId, scopes, state }`. Aceita `state` `ativa` e `rotacionando` — as duas versões válidas simultâneas do §2 do contrato.

`revogarCredencial(id)` — marca `state = 'revogada'` e `revoked_at = now()`.

`resolverMembroAgenteDoPipeline(workspaceId)` — localiza o Membro que ocupa o Papel `rol_sp_agente_pipeline` do catálogo; recusa se não existir, com mensagem que aponta o Plan 02-08. A credencial guarda `member_id`, mas a emissão confere que ele é de fato o Agente do pipeline, para que ninguém emita uma credencial de serviço apontando para um Membro humano.

Criar `apps/api/src/servicos/credencial.cli.ts` com subcomandos `emitir --nome=<n> --escopos=payment-requests:read,payment-requests:write`, `rotacionar --id=<id>` (emite a nova, marca a antiga como `rotacionando`, imprime o prazo de graça sugerido) e `revogar --id=<id>`. A saída imprime o segredo **uma única vez**, com aviso explícito de que ele não será mostrado de novo; todos os outros comandos imprimem só `id`, `nome`, `scopes`, `state` e datas.

Acrescentar a `apps/api/package.json` o script `"credencial": "vite-node src/servicos/credencial.cli.ts"`.

Criar `apps/api/src/plugins/autenticacao-servico.ts` exportando `registrarAutenticacaoDeServico(app, opcoes)`, com a mesma forma de `registrarAutenticacao`: `decorateRequest("servico", null, [])` e um hook `onRequest` — mas encapsulado num plugin Fastify aplicado somente ao prefixo `/v1/integrations`, para que o hook humano não corra nessas rotas e o hook de serviço não corra nas demais.

Comportamento do hook:
  - rota marcada `config: { publica: true }` passa direto (nenhuma rota de integração será pública, mas a simetria com o hook humano é intencional);
  - sem `Authorization: Bearer` → `401` com `erroDoContrato("CREDENCIAL_AUSENTE", requestId)`;
  - token que não resolve → `401` `CREDENCIAL_INVALIDA`; a resposta é idêntica nos dois casos de falha de segredo (id inexistente e hash diferente), para não permitir enumeração de credenciais;
  - credencial válida mas sem o escopo que a rota declara em `config: { escopo: "payment-requests:write" }` → `403` `ESCOPO_INSUFICIENTE`;
  - sucesso → `request.servico = { credencialId, workspaceId, memberId, scopes }`. `request.membro` permanece `null` nessas rotas: quem escreve é o serviço, e o `actingMemberId` das operações vem de `request.servico.memberId` (o Agente do pipeline), nunca de nada que o corpo mande.

O hook lê `X-Request-Id` do header quando presente e o gera quando ausente, guardando em `request.id` para aparecer no envelope de erro e no log — nunca logar o header `Authorization`.

Em `apps/api/src/app.ts`: registrar `registrarAutenticacaoDeServico` como plugin encapsulado com `prefix: "/v1/integrations"`, depois de `registrarAutenticacao` e antes das rotas. Ajustar a allowlist de CORS para que `/v1/integrations/*` NÃO responda a origens de navegador: o `automation/` é servidor-a-servidor e não precisa de CORS; manter a allowlist atual (`webOrigin`) apenas para as rotas existentes. Acrescentar `PUT` à lista de `methods` do CORS somente se alguma rota de navegador passar a usá-lo — as rotas de integração não são chamadas pelo navegador.

Atualizar `apps/api/src/plugins/CONTEXT.md` com a seção "Duas autenticações, dois atores": JWT do Supabase → Membro humano por `userId`; credencial de serviço → Membro `Agente do pipeline` por `member_id` da credencial; a regra de que nenhum dos dois aceita id vindo do corpo; e a nota de que este é o caminho que a Fase 4 reutiliza (D-22 / OQ-SYN-01).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `automation/` (VPS) → `apps/api` | credencial de serviço atravessa TLS; entrada totalmente não confiável |
| credencial de serviço → identidade de Membro | uma credencial apontando para Membro humano daria privilégio amplo e auditoria falsa |
| navegador → `/v1/integrations/*` | nenhuma origem de navegador deve alcançar essas rotas |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-12 | Spoofing | `resolverCredencial` | mitigate | sha-256 + `timingSafeEqual`; segredo nunca persistido; respostas de falha idênticas (caso (b)) impedem enumeração |
| T-02-12 | Elevation of Privilege | `request.servico.memberId` | mitigate | `emitirCredencial` confere que o Membro ocupa `rol_sp_agente_pipeline`; corpo da requisição nunca altera o ator (caso (h)) |
| T-02-12 | Elevation of Privilege | escopos | mitigate | rota declara `config: { escopo }`; escopo insuficiente é 403, provado pelo caso (d) |

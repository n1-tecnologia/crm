Criar `apps/api/src/servicos/idempotencia.ts` exportando
`comIdempotencia<T>({ servicoId, rota, chave, requestHash }, executar: () => Promise<{ status: number; corpo: T }>)`:
  1. `insert ... on conflict do nothing` com `status='in_progress'`. Se inseriu, seguir;
  2. se não inseriu, ler a linha: `request_hash` diferente → devolver `409 IDEMPOTENCY_KEY_REUSED`; `status='in_progress'` → devolver `409 REQUEST_IN_PROGRESS` com `Retry-After: 2`; `status='completed'` → devolver `response_status`/`response_body` gravados;
  3. executar a operação; gravar `status='completed'` com a resposta; devolver.
Se `executar()` lançar, apagar a linha `in_progress` (para não travar a chave) e propagar. `requestHash` é sha-256 do corpo canonicalizado (chaves ordenadas), calculado pela rota.

Criar `apps/api/src/servicos/dto-solicitacao.ts` exportando:
  - `paraDtoV1(state, task, { urlDeDownload })` — projeta uma Tarefa da Lista de Solicitações em `PaymentRequestDtoV1`, lendo os valores dos 25 Campos pelos ids literais do catálogo e aplicando o de-para do §4 do contrato. `Valor` vira `amountCents` inteiro (multiplicar por 100 com arredondamento, nunca float no contrato). Datas viram `YYYY-MM-DD`. `attachments[]` chama `urlDeDownload(objectKey)` para cada `WorkspaceFile` ligado, preenchendo `downloadUrl` e `expiresAt` — gerados agora, nunca lidos de armazenamento;
  - `paraCommentDtoV1(state, comment)` — projeta um Comentário, resolvendo `author` para `{ kind, id, displayName }` a partir do `ActorRef` (inclusive `sistema/Formulário` e o Agente do pipeline).
Uma Tarefa de outra Lista projeta `fail`/`undefined`: só Solicitações atravessam este contrato. Campo ausente vira `null`, nunca string vazia nem valor inventado.

Leituras (escopo `payment-requests:read`, sem `Idempotency-Key`):
  - `GET /:taskId` → hidrata, projeta com `paraDtoV1`, 404 se não for Solicitação;
  - `GET /` com `cursor`, `limit` (máx. 100) e `updatedAfter` → ordem estável `(updatedAt, id)`, cursor opaco (base64 de `updatedAt|id`), `nextCursor` ausente na última página;
  - `GET /comments/:commentId/replies` com `cursor`/`limit`.

Escritas (escopo `payment-requests:write`, `Idempotency-Key` obrigatório — ausência é `400`):
  - `POST /:taskId/comments` `{ text, parentCommentId?, mentionMemberIds? }` → `addTaskComment` dentro de `executar()`, com `opcoes.eventos` emitindo `solicitacao.comentario-criado.v1`; responde `CommentDtoV1`;
  - `PUT /:taskId/tags/:tagId` → `setTaskTags` com união (set-like); 200 tanto se já existia quanto se criou;
  - `PUT /:taskId/due-date` `{ dueDate: string | null }` → `updateTask`;
  - `PUT /:taskId/status` `{ status, reason? }` → `changeTaskStatus`; mudar para o mesmo valor é 200; transição inválida é `422` (regra de domínio), não 400.

Regras comuns, a aplicar em todas:
  - `actingMemberId` = `request.servico.memberId`; nenhuma rota lê id de ator do corpo;
  - toda escrita passa por `comIdempotencia` com `servicoId = request.servico.credencialId` e `rota` = o template (não a URL com ids, para a chave não depender de formatação);
  - erro de schema → `erroDoContrato("SCHEMA_INVALIDO", requestId)` com `400`, detalhe completo só em `request.log.warn` (o mesmo padrão de `operacoes.ts`);
  - recusa de domínio (`OperationResult.ok === false`) → `422` com `REGRA_DE_DOMINIO` e a mensagem do domínio (que já é pt-BR e sem dado interno);
  - conflito de revisão da UoW → `409` `CONFLITO_DE_REVISAO` com `retryable: true`;
  - nenhuma rota loga corpo financeiro; `request.log` recebe `{ rota, taskId, requestId, status }` e nada mais.

Em `apps/api/src/app.ts`, registrar `rotasDeIntegracaoDeSolicitacoes` dentro do plugin encapsulado que o Plan 02-09 criou para `/v1/integrations`.

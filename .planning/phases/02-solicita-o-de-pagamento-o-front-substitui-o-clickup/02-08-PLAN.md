  <action>
Tornar `ImposedLimits.tasksPerList` mutável em `packages/dominio/src/types/workspace.ts` (remover `readonly` só deste campo) e documentar no tipo que a elevação é decisão consciente registrada em Atividade — `02-RESEARCH.md` exige elevar o limite antes do dry-run da importação, e contorná-lo por SQL é o antipadrão que se quer evitar.

Criar `packages/dominio/src/solicitacao-de-pagamento-evolver.ts` exportando:

`evoluirConfiguracaoDeSolicitacoes(state: DataState, actingMemberId: Id, opcoes?: { tasksPerListMinimo?: number }): OperationResult<DiffDeConfiguracao>`

Comportamento, na ordem:
  1. localizar o Espaço `Gestão` e a Pasta `Financeiro` pelos ids literais que `bootstrap-gestao.ts` usa; recusar com mensagem clara se não existirem (esta fase não recria o bootstrap da Fase 1);
  2. para cada elemento do catálogo (Lista, Status, Campos, Tag, Papéis), aplicar a regra **criar-ou-conferir**: se o id não existe, criar; se existe, comparar campo a campo com o catálogo e acumular divergência;
  3. se houver qualquer divergência, devolver `fail` com um resumo legível — `DiffDeConfiguracao` carrega `criados: string[]`, `conferidos: string[]`, `divergentes: Array<{ id, campo, esperado, encontrado }>`;
  4. elevar `state.workspace.limits.tasksPerList` para `max(atual, opcoes?.tasksPerListMinimo ?? 5000)` e registrar a elevação no diff quando ela acontecer;
  5. registrar uma Atividade por elemento criado e uma pela elevação do limite, com `memberActor(actingMemberId)`;
  6. devolver `ok(diff)`.

Regras duras, a registrar como comentário no arquivo:
  - a função nunca remove nada: Status, Campo, Tag ou Papel a mais no estado é divergência reportada, não item deletado;
  - a função nunca toca `state.tasks`, `state.comments` nem valores de Campo;
  - ids são os literais do catálogo, nunca `nextId` — reexecutar não pode gerar id diferente do já gravado (a mesma regra do cabeçalho de `bootstrap-gestao.ts`).

`EVENTOS` — objeto `as const` com os três tipos de evento da fase e o schema zod do payload de cada um:

Criar `apps/api/src/persistencia/outbox-worker.ts` exportando `criarOutboxWorker(opcoes: { destinoUrl: string; token: string; workerId: string; relogio?: Relogio; maxTentativas?: number; fetchImpl?: typeof fetch })`, com:

`reivindicar()` — `update plataforma.integration_outbox set status='delivering', locked_at=now(), locked_by=$1, attempts=attempts+1 where id = (select id from plataforma.integration_outbox where status='pending' and available_at <= now() order by available_at, id limit 1 for update skip locked) returning *`. O `for update skip locked` é o que permite duas instâncias sem duplicação.

`entregar(evento)` — `POST` ao `destinoUrl` correspondente ao `event_type`, com `Authorization: Bearer <token>`, `Idempotency-Key: <id do evento>` e `X-Request-Id`. Classificação da resposta:
  - 2xx → `status='delivered'`, `delivered_at=now()`;
  - rede, timeout, 408, 429, 5xx → `status='pending'` com `available_at` calculado pelo backoff;
  - 400, 401, 403, 404, 422 → `status='failed'` imediato (permanente);
  - ao atingir `maxTentativas` (padrão 10) → `status='failed'`.

`backoff(tentativa)` — a escada de `02-RESEARCH.md` (imediato; 5 s; 30 s; 2 min; 10 min; 30 min; depois 30 min) com jitter de até ±20%, usando o `Relogio` injetado para o instante base. Exportar a função para que o teste a exercite sem esperar.

`sanitizarErro(erro)` — devolve `{ code, summary }` onde `summary` tem no máximo 200 caracteres e passa por uma lista de remoção: qualquer trecho que case com padrão de CPF, CNPJ, chave Pix, `Bearer `, `token=` ou URL com query string é substituído por `[removido]`. É esse valor que vai para `last_error_summary` e para `request.log.warn` — nunca o corpo da resposta cru.

`iniciar()`/`parar()` — laço com intervalo configurável; o worker roda dentro do processo `apps/api` (é o suficiente para esta fase, e o lease permite duas instâncias), ativado por `OUTBOX_WORKER_ATIVO`. Em `apps/api/src/index.ts`, iniciar o worker somente quando `OUTBOX_WORKER_ATIVO === "true"` e parar no `SIGTERM`. `buildApp()` continua sem saber do worker — a separação "montar" vs "escutar" do cabeçalho de `index.ts` vale igual aqui.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| transação da plataforma → rede | uma chamada HTTP dentro da transação prenderia conexão e acoplaria durabilidade a disponibilidade alheia |
| payload do evento → `automation/` | tudo que entra no payload cruza a fronteira sem as garantias do contrato v1 |
| duas instâncias do worker → mesmo evento | entrega dupla vira pagamento processado duas vezes |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-16 | Tampering | `gravarEventos` + índice único | mitigate | evento no mesmo `pg.Client` antes do commit; índice único parcial do Plan 02-03; casos (a)–(e) |
| T-02-16 | Tampering | derivação por diff | mitigate | eventos vêm de `opcoes.eventos(valor, state)` fornecido pela rota, nunca do `diferenca` — a importação histórica (Plan 02-22) simplesmente não passa `eventos` |
| T-02-13 | Denial of Service | lease do worker | mitigate | `for update skip locked` + `locked_by`; caso (l) prova entrega única com duas instâncias |
| T-02-14 | Information Disclosure | `last_error_summary` e logs | mitigate | `sanitizarErro` remove Bearer, CPF/CNPJ, chave Pix e query string; caso (m) prova |
| T-02-14 | Information Disclosure | `payload` do evento | mitigate | schemas `.strict()` no catálogo `EVENTOS`; caso (f) prova que só as chaves declaradas existem |
| T-02-17 | Repudiation | replay do mesmo evento | mitigate | `Idempotency-Key` é o `id` do evento e não muda entre tentativas; caso (i) prova |
| T-02-05 | Availability | `automation/` fora do ar | mitigate | D-19: evento fica `pending` e o envio público já foi confirmado; nenhuma dependência síncrona |
</threat_model>

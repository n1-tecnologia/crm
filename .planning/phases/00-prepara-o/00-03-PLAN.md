<objective>
Implementar o coração de PREP-02: `exportarClickUp(opcoes)` em `apps/api/src/importacao/clickup/exportar.ts` — a orquestração Lista → Campos → Membros → Tarefas (duas passadas: `archived=false` e `archived=true`) → detalhe por Tarefa → Comentários → `time_in_status` → anexos, gravando o JSON bruto um arquivo por recurso e por página (D-03), anexos baixados com caminho sanitizado (D-04), retomável a partir do disco (RESEARCH Pitfall 4), sem Postgres, sem log de token — com testes unitários contra um cliente falso (sem rede, fixtures no formato da documentação, nunca dado real — D-02).

Purpose: é o que produz o insumo da importação (Fases 2/3) e a base da prova de paridade (CON-09). O desenho "um arquivo por página + gravação atômica + pular o que já existe" é o que torna viável uma exportação de 3.000+ requisições a 100 req/min (35-45 min só para a Lista de Solicitação) que pode cair no meio e continuar.

Escopo honesto de "histórico de status" (critério 2 do ROADMAP): a API pública v2 do ClickUp NÃO tem endpoint de histórico cronológico de status (RESEARCH.md Pitfall 1, citado de `feedback.clickup.com`). Este plano entrega o que a API dá: `GET /task/{id}/time_in_status` (tempo acumulado por status, dependente do ClickApp "Total time in Status") gravado por Tarefa quando disponível, decidido por um smoke test na primeira chamada; mais os Comentários datados e `date_created`/`date_updated`/`date_closed` de cada Tarefa. A reconstrução aproximada de transições fica para a spec (PREP-03), por amostragem, como `contas-a-pagar.md` fez.

Output: `exportar.ts` + `exportar.test.ts`. O CLI, o manifesto e o teste de integração chegam no Plan 00-04; a execução real no 00-05.
</objective>
